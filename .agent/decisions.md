# Decisions (ADR log, append-only)

Format: `[ADR-00N] decision — why — rejected alt (date)`

- [ADR-001] MCP server only, no web app yet — Marcos's call: work conversationally over the data for a few weeks and build UI only once we know which questions actually help, so no code gets thrown away — rejected: `src/modules/lol/` inside athlete-os now, standalone Next.js repo now (2026-08-14)
- [ADR-002] The benchmark for "where am I losing vs my elo" is built from the OTHER players in his own matches, not from an external rank average — match-v5 returns all 10 participants, so every match yields exactly one same-role peer that Riot already MMR-matched to him, at zero extra request cost; sampling hundreds of Platinum players would cost thousands of requests against a 100/2min limit — rejected: league-v4 ladder sampling, third-party aggregate sites (different methodology, unverifiable) (2026-08-14)
- [ADR-003] Zero-dependency runtime except the MCP SDK — Node 24 ships native `fetch`, native `node:sqlite`, and native TypeScript type-stripping, so there is no HTTP client, no DB driver, and no build step to maintain — rejected: better-sqlite3 + axios + tsx (three deps and a build step for capabilities already in the runtime) (2026-08-14)
- [ADR-004] Store the full raw match JSON alongside flattened columns — matches are immutable once played, so the cache never needs invalidating, and a metric we did not think to flatten today can be derived tomorrow without re-hitting the API — rejected: flattened columns only (would force a re-backfill for every new metric) (2026-08-14)
- [ADR-006] Three layers, split by what each is good at: (1) THIS repo becomes `lol-lab`, the local engine — ingest, derive, analyse — with the analysis extracted to a pure library and two thin front-ends over it (the existing MCP for conversational queries, a NEW CLI for the rituals, since a 40-fight report does not fit an MCP response and the nightly sync is a scheduled task, not a chat turn); (2) athlete-os receives ONLY the daily aggregate, 4-6 metric_keys through the `import_observations` path ADR-024 already built, so its ADR-025 pattern engine correlates sleep/HRV/load against LoL outcomes with ZERO new statistics code; (3) the vault stays the decision layer (CSV aggregates to `_raw/lol/`, proposed frontmatter on existing notes, no new note types) — why: the rate-limited ingest, the ~200MB raw-timeline cache and the heavy per-game derivation are local-batch concerns that do not belong in a Vercel/Supabase app, while athlete-os genuinely needs only a handful of numbers a day, which is exactly what its spine was designed for — this honours athlete-os ADR-005/010 (LoL is the second module of the all-in-one) without dragging the match database into Supabase — rejected: everything inside athlete-os `src/modules/lol/` (timelines in Supabase, 24h-rotating-key rate-limited ingest on Vercel), a brand-new repo (throws away 38 tests and a pipeline already verified against op.gg) (2026-08-16)
- [ADR-007] Capture and output contract: ~30s per session (one tap per game — lost by me / lost anyway / even — plus tilt 1-5 at session close), and the primary output is markdown in the terminal PLUS writes to the vault — why: the per-game tag is the only thing that separates "I played badly" from "I got a bad team", and without it every defeat weighs the same; anything beyond it is the high-friction capture athlete-os already documented as habit-killing. No dashboard: Marcos asked for what to do differently next game, not for something pretty — rejected: zero manual input (can never attribute a loss), free-text note per defeat (friction), terminal-only (leaves the second brain unfed), a local web page now (deferred to an optional Fase 5, for the two things text does badly: the gold curve and the death heatmap) (2026-08-16)
- [ADR-008] Timeline capability map, measured across all 67 backfilled timelines BEFORE the event layer was designed (the Fase 0 verification the plan required): `frameInterval` is 60000ms on every match, so participant POSITION is sampled once a minute and nothing finer can be reconstructed from frames. But kill-type events carry their own exact timestamp AND position — CHAMPION_KILL 4364/4364, ELITE_MONSTER_KILL 619/619 — so fight clustering by time+space is EXACT and does not depend on frame sampling at all, which retires the "fight clustering will be approximate" risk the plan carried. CHAMPION_KILL also carries `victimDamageReceived`/`victimDamageDealt` (populated 4364/4364, one entry per participant who dealt damage) plus `victimTeamfightDamageDealt/Received`, which makes "was he IN this fight" answerable exactly — including the fights where he neither killed, assisted nor died — instead of via a positional proxy. THE ONE LOSS: `WARD_PLACED` and `WARD_KILL` carry only `creatorId`/`killerId`, `wardType` and `timestamp` — NO position, confirmed 0 of 13457 ward events across the corpus. So ward heatmaps and the planned "muerto a oscuras" metric (deaths with no friendly ward covering the area) are NOT BUILDABLE from the API and are cut, not deferred. Vision keeps what survives and is arguably the more actionable half anyway: ward placement TIMING relative to objective spawns, control-ward cadence by type, and ward-clear timing — all timestamp-only — rejected: inferring ward position from the creator's frame position at the nearest minute (up to 60s of walking between the two, an invented number dressed as a measurement) (2026-08-16)
- [ADR-009] The headline metric is STATE-CONDITIONED conversion, not the season mean: freeze the game at minute 14, bucket by gold difference versus the lane opponent (atrás / pareja / arriba), and ask what he does from each state — with his opponents' conversion from the SAME state as the peer baseline, keeping ADR-002's shape but applying it to a state rather than an average. Enforced structurally: `Metric.contamination` is required, and `benchmark()` refuses to rank a `contaminated` metric unless the caller declares a `stratum`, so no contaminated metric can headline a report again (G-008, machine-checked in tests/contamination.test.ts). The even bucket deliberately reports no peer comparison — there the two rates are complements and comparing them says nothing. The 500-gold band is a JUDGEMENT CALL over a smooth distribution with no natural cut, so `conversionByBand` sweeps 300/500/750/1000 and `conversionIsRobust` only blesses a finding whose direction survives every band — why: the season-mean benchmark said he was ahead in 17 of 18 metrics at a 52.8% win rate, because 14 of 18 are downstream of winning and his stomps dominated every mean; conditioning on a pre-outcome state is the only way a mean stops measuring "when I win, I win big" — rejected: comparing his means to an external rank average (unverifiable, and the contamination survives it), dropping contaminated metrics from the catalogue entirely (they are still worth SHOWING as description, just never as a ranked leak), a single fixed gold band (a finding that only holds at one arbitrary cut is an artefact of the cut) (2026-08-16)
- [ADR-010] The hypothesis ledger freezes the ANALYSIS SPEC, not just the claim, and registration carries a TIMESTAMP plus TWO boundaries — the spec (account, role, queue, minute, band, outcome variable, stratum, champion) is canonicalised and hashed at registration, `evaluateHypothesis` refuses any spec whose hash differs (G-013), a type-level assertion fails `tsc` if a field is added to the spec without being listed in the canonical key order, and exactly ONE measure function dispatches on the spec so that identical hash implies identical computation; registration stores `baseline_until` and `test_from` separately, making the games between them a declared, counted hole rather than a silent choice — why: the plan's ledger stored date · claim · metric · direction · effect · n_needed, and the 2026-08-16 audit showed the missing fields were the load-bearing ones. The Fase 0 finding survived a sweep of the gold band and failed a sweep of the MINUTE, a knob nobody had turned; an out-of-sample evaluation free to re-choose that knob inherits exactly the researcher degrees of freedom that manufactured the finding, so the ledger would have laundered noise instead of catching it. The two boundaries came from the same day: three games arrived hours after the finding existed and before it was registered, so a single date would have silently assigned them to whichever side flattered the claim — rejected: storing the spec as typed columns (a new knob could be added without touching the hash), passing a measure function alongside each hypothesis (two evaluations could share a hash and compute different numbers), a single registration date (ambiguous the moment he plays on registration day), moving the baseline forward to absorb the three games (moving a baseline to where the number looks better is the disease, not the cure) (2026-08-16)
- [ADR-011] The cross-account rule is enforced by the TYPE SYSTEM plus one refusing function, and performance counters leave the vault entirely — `MATCHUP_PERSPECTIVE` is a mapped type over every numeric field of `MatchupRow`, so adding a number to that row fails `tsc` until it is classified `conocimiento | rendimiento`; `pool()` sums a field but throws `CrossAccountError` if the field is `rendimiento` and the rows span more than one account, which makes a pooled win RATE unreachable because its numerator cannot be built; performance questions are answered by `breakdown()`, which returns the per-account split. On the vault side the hand-maintained `partidas`/`wins` counters in `matchup` and `champ` notes are retired in favour of `_raw/lol/matchup-record.csv`, written by the engine with `cuenta` and `cola` on every row — why: `/lol` incremented those counters without reading `cuenta`, so the main's first ranked game would have merged a fresh-MMR climb into Platinum 2 numbers silently, and the note recorded no scope of its own (`matchup` has no `alcance` key, so `partidas: 1` meaning "1 in the last 20 games" reads as "1 ever" to any later reader); the engine already holds every game with its account, so the record is derived exactly instead of kept twice. The shrinkage estimate in `prep.ts` follows from the same rule: it uses ONLY the record of the account about to be played, while reps pool across accounts — rejected: suffix keys per account in the notes (`partidas_main`/`wins_main`, follows the flex precedent of vault rule 10 but multiplies with every account × queue and leaves "unsuffixed = smurf" as a tacit default), nested YAML per account (Bases cannot query it), passing the perspective at the call site (the caller could simply lie), deleting the existing counters (a vault schema change never deletes loaded data — they are frozen as historical instead) (2026-08-16)
- [ADR-012] The growth curve's confound underlay is the lane opponent's ABSOLUTE value of the same metric, not rank or MMR — measured per game from the cache, drawn on the SAME scale as his own rolling line — why: roadmap §5b required rank/MMR drawn underneath so a jump could be attributed, and that turned out not to be buildable. Verified 2026-08-16 rather than assumed: match-v5 carries no rank, tier, LP or MMR field on any of its 156 participant keys, so the underlay is not derivable retroactively for a single past game; league-v4 (already wired in the client) returns the account's CURRENT standing only, which could start a series today but says nothing about the 39 games already played. The opponent's absolute level is available for every game ever cached, and it tracks the thing that actually contaminates the comparison — lobby strength — rather than a label correlated with it. Same scale for both series is part of the decision, not a rendering detail: separate axes would let a flat pair read as divergence, which is the exact misreading the underlay exists to prevent. The curve also refuses any metric not classified `causal` (G-008), which in today's catalogue leaves `cs_first_10` as the only usable one, since `early_lane_adv`/`lane_adv` are binary flags (G-009) and `turret_plates` is contested (roadmap §4.4) — rejected: waiting for league-v4 snapshots to accumulate before shipping any curve (throws away the history we have), inferring rank from op.gg's `tier_promedio_partida` (exists for 20 games only and needs a manual pull), a fitted regression slope instead of endpoint drift (at this n a fitted line invites a p-value, and this project reports effect and n) (2026-08-16)
- [ADR-013] "Expensive" is ONE measured quantity — the team gold swing over the two minutes after the event — and everything else about the moment is reported beside it, never folded into the ranking; a fight is a cluster of ≥3 champion kills, smaller clusters are pickoffs and counted apart — why: a composite cost blending bounty, objective loss and gold swing needs three weights, none of them derivable, all invisible in the output, which is exactly the class of arbitrary knob G-011 exists to catch; gold swing is a single number that answers what the word "expensive" actually asks, and leaving bounty/solo/objective as description keeps them legible instead of buried in a coefficient. The ≥3 threshold comes from the plan and was dropped in the first implementation, which made every isolated 1v1 its own "fight" — a 24-minute game reported 35 of them and "present in 13 of 35" read as an indictment for not teleporting across the map to solo kills; verified afterwards that the clustering itself is sound (62 CHAMPION_KILL events against 62 kills summed over the ten players, all of them landing in a cluster), so the defect was the threshold, not the clustering. Deaths whose two-minute window runs past the end of the game are dropped from the ranking and counted, not scored 0, because a sort ascending would otherwise put the least measurable event first. Solo-death detection is defined from EVENTS (no other champion died within the fight window) rather than from ally positions at the nearest minute frame, which would be up to 60 seconds of walking away — the same substitution ADR-008 already rejected for ward positions — rejected: a weighted composite cost score, ranking by bounty alone (ignores what the death actually cost the team), inferring "was he alone" from frame positions (2026-08-16)
- [ADR-014] Fase 5 built at Marcos's request 2026-08-16: ONE self-contained local HTML file, two views only — the gold differential against the lane opponent over time, and the death map — generated by `scripts/page.ts`, no deploy, no framework, no build step, inline CSS and inline SVG (consistent with ADR-003 and with the harness's Scope Guard, which defers to the repo's reality over the locked web stack). It is explicitly NOT a dashboard: ADR-007 stands, and the per-game report lines stay in the terminal because "min 17:30 you died alone with your team 6.6k up" is already the best form that fact has. Two correctness decisions inside it are load-bearing and tested: (1) the projection FLIPS Y, because League's y grows toward the top of the minimap and SVG's grows downward — without the flip the map is upside down, top lane reads as bot lane, and every conclusion off it is inverted while looking perfectly plausible; (2) positions are NOT mirrored to normalise "his side" into a fixed corner, which was the first instinct and is wrong — Summoner's Rift lanes are absolute and shared, bot lane is the same physical lane for both teams, so rotating or reflecting to tidy the map would swap top and bot lane identity; the team-relative fact is computed instead (`isOwnHalf`, from the anti-diagonal `x + y = MAP_MAX` and the side he was on THAT game) rather than moved. Map bounds were measured before being trusted: across 2493 kill events x runs 430..14153 and y 514..14247, so the nominal 0..14820 clips nothing. Sanity-checked after building: 62% of his deaths fall within 2500 units of the mid axis, which is what a mid laner's map should look like — rejected: a dashboard of aggregates (the thing that already misled this project once), Next.js per the harness's locked stack (this repo has no build step by ADR-003), normalising the map by rotation or reflection, auto-scaling the gold axis (would put zero near an edge and make a small lead look like domination — the scale is symmetric about zero with a floor) (2026-08-16)
- [ADR-005] The key is read from `.env` on EVERY request, not cached at boot — development keys expire every 24h, and re-reading turns rotation into "paste and keep going" instead of "restart Claude Code" — rejected: read once at startup, a `riot_set_key` tool (would put the secret in the chat transcript) (2026-08-14)
- [ADR-015] The per-game tag is a REPORTED field and is fenced off from every peer comparison by construction — `TAG_PROVENANCE` classifies each field of `TaggedRow` as `reported | derived`, `peerComparable` throws on a reported one, and `splitByTag` has deliberately no peer counterpart beside it — why: ADR-002's whole trick is that every match ships nine other players Riot already MMR-matched, so a peer baseline is free; none of them tagged anything, so a tag-conditioned rate compared against "his peers" compares against an empty other side and returns a number anyway. Two further properties of reported data are enforced rather than documented: the tag is self-assessment and therefore correlates with the result (losing re-reads the game), so it may SPLIT populations of defeat and never explain them, and no n fixes that; and it decays, so `tagged_at` is always stored and the lag is measured against the game's END rather than its start, because a 40-minute game tagged at its own end time would otherwise read as 40 minutes of decay that never happened. Tilt is `number | null` and never optional: "he declined to answer" and "the caller forgot to ask" must store the same value and it must not be a middling 3. Two tables rather than one, because tilt is a property of the SITTING and the tag of the GAME; one row would force the tilt to be repeated per game or invented — rejected: one table with a tilt column per game, a defeat-only questionnaire (stops being filled in during a good week, and then the missing rows are not missing at random), inferring the attribution from the data (this is the one input the cache cannot produce, which is the entire reason ADR-007 bought thirty seconds a session) (2026-08-18)
- [ADR-016] ONE ritual, `lol cerrar`, and the weekly review is folded into it rather than existing as its own command — Marcos asked to build `lol review` and then chose the post-session moment as the ONLY moment he wants the software to speak, so the review's CONTENT (hypotheses that moved, coverage gaps in the matchups just played) appears inside the closing ritual and only when it has something to say; `insufficient_n`, which is the correct answer for months, is deliberately not printed. Capture runs BEFORE any computation and each tag is committed the moment it is typed: the sync and the rank snapshot are both allowed to fail without ending the ritual, because the development key expires every 24h and losing a night's tags to an expired key trades the irreplaceable half of the input for the replaceable one. Verified by cutting stdin mid-session rather than asserted: both tags typed so far survive, and the session row stays honestly open with `closed_at` and `tilt` NULL — why: a ritual that reports "nothing changed" every night trains him to skip the night it does not, and the daily ritual with the most friction is the one that does not get done — rejected: a separate `lol review` on a weekly cadence (a moment he said he would not use), threshold alerts (same), batching the tags to the end of the loop (one error costs the whole session's input) (2026-08-18)
- [ADR-017] The engine NEVER writes markdown into the vault: it writes CSV to `_raw/lol/` and nothing else — why: vault rule 2 says a contradiction is surfaced, never overwritten, and honouring that mechanically from outside the vault means designing a merge policy, a set of touchable frontmatter keys and a conflict surface, all to automate a paste; refusing the write makes the rule unbreakable instead of enforced. It also settles roadmap §3.4, which had blocked every vault write pending exactly that design. The CSV path already exists and works (`export-matchup-record.ts`), and ADR-011 already moved the performance counters out of the notes for independent reasons — rejected: the engine writing agreed frontmatter keys (needs the merge design, and the first wrong write is silent), printing a suggested block for him to paste (better, but it is still the engine authoring vault content and the CSV already carries the same facts in a form Bases can query) (2026-08-18)
- [ADR-018] The UI becomes an EXECUTION surface: `lol ui` boots a local `node:http` server on 127.0.0.1 and the browser drives the ritual, the sync and the reading by click — which revises ADR-001 ("MCP only, no web app yet"), ADR-007 ("markdown in the terminal, no dashboard") and ADR-014 ("one static page, two views"), all three at Marcos's request — why: the static page CANNOT act. It is opened over `file://`, so it cannot sync, cannot reach the Riot API (the key would be exposed and CORS blocks it regardless) and cannot write to SQLite; a local process is the only shape that does what he asked for, and this is a THIRD front-end over the same pure `src/analysis/*` (ADR-006) rather than a second engine. What ADR-007 actually banned survives intact and is restated here: a wall of aggregates must never REPLACE the per-game actionable line, so the three expensive moments with their exact minute stay at the top of the page and every number carries its n and its scope by reusing the strings `confidenceOf`, `CoverageScope` and the ledger caveats already produce — the page re-derives nothing. Three properties are structural rather than conventional: (1) the tag is written ONE REQUEST PER GAME and the write lands before the response, so closing the tab after three clicks leaves three tags on disk — verified by SIGKILLing the server mid-ritual, not asserted; (2) the panel endpoint spends ZERO Riot requests, which is what makes polling it safe against the 100-per-2-minutes budget; (3) a per-boot token plus an Origin check on mutating requests, bound to 127.0.0.1 and never 0.0.0.0, because any page he visits can POST to localhost and this process holds the key — that is fifteen lines, not the application security he asked me not to spend effort on. The key value never reaches the browser at all, pinned by a test asserting the payload's SHAPE so adding a `masked` field fails rather than leaks. Auto-refresh polls the panel only and never the tagging list, because re-rendering that list under his hands would reset the buttons mid-ritual — rejected: a scheduled task or Windows service (nothing should run when he has not opened anything, D8), a static page that only says what to run (what he asked for as a fallback, and it is still a to-do list he has to obey by hand), any framework or build step (ADR-003), sending `masked` to the page (useful for nothing the panel cannot say without it) (2026-08-18)
- [ADR-019] The tagging backlog is closed by a DATED DECISION, not by tagging it and not by a filter — `settings.tag_cutoff` holds the moment Marcos decided to stop being asked about games already played, `untaggedGames` excludes anything that ENDED before it, and `abandonedByCutoff` keeps counting what was left so the panel states the cost (81 games: 71 smurf, 10 main) instead of quietly showing zero — why: he said it himself the day the UI arrived — he does not remember the older games and will tag from now on — and ADR-015 already draws exactly that line, since a tag typed from two-week-old memory is a different measurement from one typed after the session and would enter the same column. The alternative failure modes are both real: leaving 81 games pending makes the panel's one urgent action permanently unachievable, which trains him to ignore the urgent actions that are achievable, and silently dropping old games would hide a judgement call inside a SQL clause. The cutoff is compared against the game's END rather than its start, matching how the tag lag is measured, so a game that was running when he pressed the button stays askable; the button lives in the fold where the backlog is already shown, beside "see the older ones", because that is the moment the choice presents itself — rejected: tagging the backlog anyway (memory, not observation), deleting the untagged games (destroys data to fix a prompt), a rolling "only the last 12 hours" rule with no record (the same effect with no date and no count, so nobody could later tell a decision from a bug), a global "hide" toggle in the page (a preference, not a fact about the data) (2026-08-19)
- [ADR-020] Item timings are back, and the item table is cached PER PATCH from Data Dragon — one catalogue per patch his cache actually contains (eight of them, 14.24 to 16.16), joined to a match by the `major.minor` prefix, and a patch Data Dragon never published is REPORTED as having no catalogue rather than read against the newest one — why: M2 cut "when does he complete his first item" on 2026-08-16 because `ITEM_PURCHASED` carries an itemId and nothing else, and the cut was correct at the time — inventing an item table was the alternative. Data Dragon removes the reason: it needs no API key, so the 24-hour rotation cannot break it; it is a different host, so it must NOT pass through the Riot rate limiter (every request spent there is a match not downloaded); and it is immutable per version, so one fetch per patch is one fetch forever. The per-patch key is the load-bearing half: an item's build path changes between patches, so a single "latest" table would silently reclassify components as finished items in old games, which is the scope error G-015 exists to prevent. `finished` is DERIVED from the data — nothing builds out of it in that patch — instead of being a list someone maintains, and the 2200-gold floor is stated in the module rather than buried, because boots and cheap finished items complete early for everyone and would crowd out the item that decides a matchup. The race against the lane opponent aligns by ORDER, not by item, since two mids rarely build the same thing and the question is tempo. WHAT IT IS NOT: a measure of how well he plays. Measured over 42 mid soloq games, his first item lands +0.34 min after his opponent's on average — but conditioned on the lane state at minute 10 it is -1.79 min when ahead, +1.69 even and +5.04 behind, so the metric is bought with gold and is reported beside the curve that paid for it, never alone — rejected: hardcoding an item table (stale within a patch and a lie the moment Riot edits a build path), one "latest" catalogue for every game (silently wrong on old games), folding the fetch into the nightly sync (a network round trip every evening to learn nothing changed), inferring "finished" from a gold threshold alone (boots and support items break it in both directions) (2026-08-19)
- [ADR-021] The panel shows PICTURES — champion portraits, item icons, the Rift minimap under the death map — and every one of them is downloaded once by `lol assets` and served by the local server, never hotlinked from Riot's CDN — why: the page's own header says "local, en tu máquina, nada de esto sale de acá", and an `<img src="https://ddragon...">` would make that false on every load: the browser would announce which champions he is reviewing, and the panel would degrade on a bad connection. 5.9 MB fetched once buys a page where a game is recognised by its portrait instead of read as a name, and the death map is read against the actual lanes instead of against an anti-diagonal. Three details are load-bearing: art is fetched from ONE version while the item TABLE stays per patch (ADR-020) — a build path changes between patches, the picture of Lich Bane does not; files are stored under the name the MATCH uses rather than Data Dragon's, so the page builds a URL from what it already has and the `FiddleSticks`/`Fiddlesticks` casing (G-016) is resolved at download time instead of failing as a broken image; and `/img/*` is served BEFORE the token check, deliberately, because it is Riot's public art carrying nothing about him, which also lets the memoised map SVG survive a reboot instead of being invalidated by every new token. Path traversal is the one real risk of serving files and is closed by `safeAssetName` plus a fixed set of three folders, asserted by test — rejected: hotlinking the CDN (breaks the page's only privacy promise), inlining images as data URIs (megabytes of base64 in every response, and no browser caching), one copy of every icon per patch (eight times the disk for identical PNGs), a chart or map library (the legibility came from the artwork, not from a renderer, and ADR-003 keeps this repo dependency-free) (2026-08-19)
- [ADR-022] A metric declares its DISTRIBUTION as well as its contamination, and only a `magnitude` may be ranked or given a percentile — `Metric.distribution` is required and never defaulted, exactly like `contamination`, so the two gates a number must clear to headline the report are independent and both explicit: G-008 asks whether it is downstream of winning, G-009 asks whether it has a size at all. A causal 0/1 flag passes the first and fails the second, which is the case that actually shipped. The declaration is a claim about RIOT's data that `tsc` cannot check, so `benchmark()` re-checks every declared magnitude against the sample it has (`looksBinary`) and demotes it by name in `notes` — rejected: dropping the two flag metrics from the catalogue (they are real and the RATE is worth reading, just not the percentile), and a heuristic that also guesses at ordinals (it would fire on turret plates and solo kills, which are counts, and a check nobody trusts gets switched off) (2026-08-20)
- [ADR-023] The panel and the CLI can register an account by themselves; MCP is no longer the only door in — `lol cuenta <Nombre#TAG> [etiqueta]` and `POST /api/cuenta` both resolve a Riot ID, and the panel shows a form instead of its reading sections while the cache holds no account — why: ADR-018 made the panel an EXECUTION surface and the very first step of the workflow was the one thing it could not execute. A fresh clone that followed the README to `pnpm lol ui` got five routes answering 404 `no conozco la cuenta 'smurf'`, one error line at a time, and nothing anywhere on the page to do about it. The same reasoning applies to the timeline hole: `riot_backfill_timelines` was MCP-only while the panel is what suffers most from a game with no minute data, so `lol backfill` exists and the panel's sync button runs the repair as a second phase — rejected: telling him to ask Claude (the ritual is a double click on a .bat, and ADR-016 says the post-session moment is the only one the software gets) (2026-08-20)
- [ADR-024] The panel is PROGRESSIVE DISCLOSURE: one card says what to do now, everything else is a collapsed section that renders the first time it is opened — Marcos's call, in his words "que no haya tanta información en pantalla de una porque si no es mucho para los ojos". Each section is a native `<details>` with a BADGE in its summary, which is the whole contract: collapsed must not mean blind, so a closed "Taguear" still says 45 and a closed "Cuentas y key" still says the key is missing. Open/closed is remembered in `localStorage` and the first visit opens only the summary; a section fetches nothing until it is opened, so the page went from nine renders and five fetches at boot to two. `<details>` rather than a bespoke accordion because it is keyboard-accessible and focus-managed for free, it survives with JavaScript off, and it is one line of markup against a component nobody would test — rejected: tabs (they hide that anything else exists, and the sync progress has to stay visible while he reads), a dashboard grid (ADR-007 rejected a dashboard once already and the reason stands: he asked what to do differently, not for something pretty) (2026-08-20)
- [ADR-025] Account, role and queue are ONE scope, chosen in the header and carried in the URL — every route takes it, the memo key includes it, and a reload lands where he was.
